## Data model

**Playbook file** — `~/.fs/kb/<name>.yaml` (global) · `~/.fs/projects/<project>/kb/<name>.yaml` (project) · `src/flagship/defaults/kb/<name>.yaml`, embedded in the binary (the **shipped default**, and the last scope rather than a copy of one)

```yaml
# required; must equal the file name
name: member
# optional, default empty = matches every dispatch. comma-separated terms, ALL
# must hold. term = `k` (present) or `k=v`
applies_when: member
# optional, default 500; ascending within each moment; ties by name
order: 20
# optional: the dispatcher this protocol's steps are written for
engine: herdr
# optional: the kind of agent that runs this work
agent: pi
# optional: the agent's own arguments, one argv element per comma-separated
# term; no shell syntax, no quoting
agent_args: --permission-mode, auto
# optional: the node kind a dispatch writes (default: `dispatch`)
creates: batch

# one section per moment the protocol takes part in; at least one section, any
# combination, any order
work:
  - say: you work in your own worktree and never touch main
  - use: dev-task — the TDD loop and the code bar
exit:
  - check: "$FS_BIN" integrated $FS_NODE
  - ask: has this member's result been read from its worker node
```

Every comment in that block owns its line, because the parser is line-oriented
and takes everything after the colon as the value: a trailing comment is *in*
the value — refused where the field is validated (`name`, `order`, `engine`,
`agent`, `creates`), and silently swallowed where it is not (`applies_when`
gains a term that can never match, `agent_args` an argument that is prose). The
rule is stated for readers of the shipped set in
`skills/flagship/references/fs-advanced.md`, and
`tests/playbooks/test_playbooks.py` fails a shipped playbook that breaks it.
**This block was the one that broke it** — every field it declares carried a
trailing comment, so `fs kb add` refused the example the Data model presents as
the format. No criterion moved with the repair; the format is the same format,
written the way the parser reads.

- Writer: the user, by hand or `fs kb add|edit`, and `fs kb reset` for a shipped default. Reader: C2. Nothing rewrites it but `fs kb reset`/`edit`.
- **A file on disk participates only when it is an override.** A body that differs from the stamp it carries, or an unstamped body that differs from the shipped default, is the user's playbook and resolves. A body that merely restates the default — stamped and current, or stamped from an older default — is **transparent**: it is not a candidate at all, and the scope below it resolves. That is what makes the shipped default a scope rather than a copy to install, and it is why nothing has to be written to `~/.fs/kb/` for the shipped set to run: `fs kb reset <name> --yes` is the only command that puts a default on disk, and it exists so the file can be edited.
- `name` must equal the file's base name — a mismatch is refused at parse.
- **`engine:`, `agent:` and `agent_args:` — how the work is realized.** Three optional fields, resolved from the plan by `resolveRealization` (C3) before any node is created. The values are never Go constants: `internal/dispatch/deliver.go`'s `agentKind = "pi"` and the literal `{engine: "herdr"}` tag set both go.
  - **Precedence is the strength of the claim.** A playbook whose `applies_when` is empty matches everything and is therefore the *standing* declaration — the default. A playbook with terms is *situation-specific* and overrides it.
  - **Two passes, because selection needs the engine tag and the resolution reads the plan.** Pass 1 reads the *standing* declarations — identifiable by an empty `applies_when`, so no selection is needed — and stamps `engine=<standing engine>` into the tag set. Pass 2 selects the plan with that tag set, then reads the *situation-specific* declarations the plan contains. The circle is broken by the fact that the standing set is known before selection; a resolution that needed the plan to choose the tag that selects the plan would be circular, and is not what this is.
  - Among situation-specific declarations, **disagreement refuses**, naming both playbooks and both values. Two plans' worth of intent cannot be averaged, so it is refused rather than resolved.
  - A plan declaring **neither** refuses, naming `worker.yaml` as the place to declare them. There is no built-in fallback: a default in Go is the policy this field exists to remove.
  - `engine:` is a **constraint** today — fs has one adapter, so a plan declaring another engine refuses rather than pretending to route. It becomes a choice when a second adapter exists.
  - The resolved `agent:` is passed through to `herdr agent start --kind`. fs does **not** validate it against herdr's kind list: that list belongs to herdr, and copying it into fs would recreate the constant this removes. An unsupported kind is refused by herdr, and the delivery rollback already handles a failed start.
  - **`agent_args:` is a comma-separated list on the field's own line, one argv element per term** — `agent_args: --permission-mode, auto`. Not a shell string: a term is passed to `herdr agent start` as a single element, so `--add-dir /tmp/x` arrives as *one* argument holding a space, and is why the separator is a comma rather than a space. A YAML block list is **not** a second spelling — this parser is line-oriented and would drop one in silence, so it is refused, naming the comma-separated form.
  - **The terms are inherited by the kind's own rule and cannot be cleared.** A situation-specific playbook declaring `agent:` and no `agent_args:` **inherits** the standing arguments: the args are what the *harness* is started with, not a property of the kind, so overriding the kind is not a reason to lose them. There is no way to declare "no arguments" — an `agent_args:` present but empty is refused, because a declaration with no terms claims arguments it does not name. A playbook that genuinely needs none simply omits it.
    - **The residual hazard, recorded rather than policed.** Inheritance is unconditional because the alternative — fs deciding which arguments belong to which kind — is exactly the kind-to-flag knowledge that stays out of fs. So a situation-specific playbook that swaps `agent:` and keeps the standing args can hand a kind arguments written for another. fs will not catch it, and herdr refuses only what it cannot encode. The authoring rule follows from where the fields sit: **`agent_args:` sits beside `agent:`, so a playbook that overrides the kind must decide what its arguments are** — declare them, or accept the standing ones deliberately.
  - **fs does not validate the tokens.** This is deliberately not `validRealizationToken`, which admits only `[A-Za-z0-9_.-]` and would reject `--settings=a=1` and any term with a space — the field is the agent's own command line, and the set of flags it may carry is the agent's, not fs's. The same reasoning that keeps herdr's kind list out of fs keeps herdr's flag grammar out of fs.
  - **`agentStartArgs` puts `--` last, and it is the start command's only emitter.** It appends the separator after every option and **only** when there are arguments: a bare `--` is a different command from the same line without one, and an argument placed before `--pane` would be read as an agent argument and leave the pane unset. The printed line that used to be a second emitter is retired — it named an agent no delivery record could reach — so there is no pair left to keep in step. Terms reach herdr as their own argv elements, so none is shell-quoted: `--kind` needs no quoting only because `validRealizationToken` already constrained it.
  - All three values are recorded on the dispatch and written to the trace's plan line, so which harness ran, and with what, is reconstructible from the record.
- **The moment is a section, not a field.** `cap:`, `entry:`, `work:` and `exit:` each hold a list of steps; a file declares the ones its participant takes part in, in any combination and any textual order — the *moment* decides when they run, never their position in the file. One file is therefore one **participant**, read top to bottom as its whole protocol, which is why `batch`, `member` and `integration` each exist once rather than twice.
- **Step kinds by moment** (the closed vocabulary; anything else is a write-time refusal naming the allowed set — checked per section, so a `do` under `entry:` is still refused at write time):
  - `cap:` → `say`
  - `entry:` → `check`, `ask`, `say`
  - `work:` → `say`, `use`
  - `exit:` → `check`, `ask`, `do`, `say`
  - `include` is allowed in every moment (it splices steps that must themselves be legal for the including section).
- **Removed fields and forms:** `type`, `trigger`, `engine_scope`, and — since the moment became a section — `phase:` together with `steps:`. A file carrying any of them is **refused** at parse with a message naming its replacement: `trigger: cap` → the `cap:` section; `type: prerequisite|cleanup` → the section of that moment plus a matching `applies_when`; `phase: entry` + `steps: […]` → an `entry:` section holding the same list; `engine_scope: herdr` → **`engine: herdr`**, the declaration that now exists, or the term `applies_when: engine=herdr` when the intent is to *match* the engine rather than declare it. `engine_scope`'s refusal is the one whose replacement changed when the field was made real: the retired field was the right field, and the fix was to make it real rather than route around it. Half-working is not an option; `fs kb diff` shows the shipped replacement and `fs kb reset <name>` applies it.

- **The key set is closed, and the parser refuses rather than ignores.** The schema is exactly the fields above plus the four moment sections; a top-level key outside it is refused, naming the field and enumerating the schema, instead of being read as an unknown line and dropped. The parser is line-oriented and cannot tell a typo from a continuation, so `agent_arg:` for `agent_args:` would otherwise parse as a playbook that simply declares no arguments — a field the author believes is set and fs has never seen. A `- ` list item is likewise refused when it does not follow a moment section: a list field written in block form lands as an empty value, and an empty value is the one shape this schema reads as "nothing declared".

**Tag set** (built per dispatch, C3)

| tag | source |
|---|---|
| `type=<T>` | `--type` |
| `engine=<T>` | the plan's resolved `engine:` declaration — not a constant |
| `member` | `--batch <node>` — this dispatch is a member of that fan-out. It does **not** also derive `batch`: if it did, `batch`'s exit section would join a member's plan and tear down at the member's close, which is the one thing the deferral exists to prevent |
| `batch` | the plan contains a playbook declaring `creates: batch` — the fan-out's own dispatch, and only it. Derived like the realization: an initial selection reads the declaration, then the plan is re-selected with the tag, so `batch`'s `exit:` section joins. One extra pass, no type-to-kind map in Go |
| `<k>` / `<k>=<v>` | `--tag`, repeatable |

Deliberately minimal: a derived tag nobody matches on is a tag nobody can trust to mean something. `cards`/`multi`/`integrates`/`project` are **not** derived — the batch gates match on `type=` instead, and a future protocol that needs a richer situation adds the tag with its first user.

**Plan** — the ordered list of `{name, moments, order}` for one dispatch, recorded as a `plan-recorded` event on the cap node with payload `{plan: [...], tags: {...}, engine, agent, agent_args}`. `moments` names the sections the playbook serves, so one entry can be both an `entry` and an `exit` participant — `batch` and `member` each are. The list sorts by `order` then name **within each moment**; a playbook serving two moments carries one `order` and uses it in both, which cannot collide because the sort never mixes moments. A new event type; additive; derived state ignores it.

**Trace** — `~/.fs/traces/<project>.<node>.jsonl`, one JSON object per line, append-only, ≤1 KiB per line, never deleted at close. One file per dispatch, filed **flat**, not under the project it acted on: the record belongs to the dispatch, whose identity is the cap node. The **project leads the name** because a person browsing the directory should recognise the file — one file is one project, since every line in it carries the same one — and a **dot** separates the halves because both contain hyphens (`fs-close-accept2`, `t-a90b8967`), which a hyphen join would blur. `project` stays a field on every line as well: the name is for a person, the field for the program, and neither can drift from the other because both are fixed for the file's life.

The cost, stated rather than glossed: the reader no longer *constructs* the path from the node. It globs `traces/*.<node>.jsonl` — a targeted glob, not the `ProjectsFor` directory walk the old nesting forced, but a lookup step. The node alone still **finds** the file; it no longer spells it.

```json
{"ts":"2026-09-21T12:00:00Z","kind":"plan","dispatch":"t-4f2a","project":"skills","tags":{"type":"dev-task","code":true},"plan":[{"name":"code","moments":["entry","exit"],"order":10}],"engine":"herdr","agent":"pi","agent_args":["--permission-mode","auto"]}
{"ts":"2026-09-21T12:00:01Z","id":"t-4f2a/code/1","dispatch":"t-4f2a","project":"skills","playbook":"code","moment":"entry","step":1,"kind":"check","status":"pass","duration_ms":12,"detail":"test -f AGENTS.md"}
{"ts":"2026-09-21T12:00:04Z","id":"t-4f2a/worker/0","dispatch":"t-4f2a","project":"skills","worker":"skills:t-9c11","playbook":"worker","moment":"work","step":0,"kind":"use","status":"loaded","detail":"handed to skills:t-9c11"}
```

- `status` ∈ `pass | fail | confirmed | loaded | skipped | refused`. There is no `followed` — see the spec's honesty NFR.
- `step` is 1-based within the playbook. `id` = `<dispatch>/<playbook>/<step>` — the trackable id.
- `worker` is written only once a worker node exists — the `loaded` and exit lines. There is nothing to name at entry, and a fabricated placeholder would be worse than an absent field.
- a step line's field is `moment`, not `phase`: the plan line says `moments` and the step line must say the same word, or one file disagrees with itself. Lines written before the schema change carry `phase` and the reader still accepts it — that is tolerance for historical records, not a second spelling.
- `detail` carries the step body, truncated; **never** the command's output.

## Boundaries & interfaces

| Pair | Contract |
|---|---|
| C2 ↔ filesystem | `Get(name)` resolves project-first, then global, then the **shipped default** — three scopes, the embedded tree last — and then **inherits**: every field and moment section the winning playbook does not declare is taken from the same-named playbook in the next scope down, and a shadow that declares nothing but its name is refused. The chain is one chain: a project playbook with no user-scope copy below it inherits from the shipped default, so the last scope is walked like the others rather than treated as a copy that happens to be missing. A file is a candidate only when it is an **override** (see Data model): a copy that restates the default does not participate, so a stale copy cannot pin the playbook it was written from, and a change to a shipped default is live with no operator step. The lookup below is the same candidate walk with the file itself on the stack, so inheritance and `include:` share one rule and cannot diverge — and a shadow naming its own playbook terminates here instead of recursing. `include:` then splices the named playbook's steps at that step's position, resolving with the *including* playbook excluded from lookup — so a project `code` that says `include: code` gets the **global** one. The two are **distinct and ordered**: inheritance chooses which fields and sections the playbook has, the splice then fills them, so a shadow whose `work:` is `- include: <its own name>` ends with the steps below once and not twice. A name already on the include stack refuses naming the chain; depth > 8 refuses. The shipped default has no path, so the stack holds a **synthetic id** for it — `"<shipped>/<name>.yaml"` — which is what the cycle check compares and what the two "came up empty" errors are told apart by. `fs kb get` marks the inherited names, because a resolved shadow is no longer self-describing. |
| C3 ↔ C2 | C3 asks C2 for every playbook name in every scope, then filters by `applies_when ⊆ tags`, sorts by `order`, name. No name-equality shortcuts remain. |
| C3 ↔ C7/C9 | `resolveRealization(plan)` returns `(engine, agent, args)` by the precedence above, **after** selection and **before** any node is created — so a refusal leaves no node and no trace. C3 stamps the engine into the tag set for the next resolution, and C7 starts the agent C3 named, with the arguments C3 resolved. Where `--` goes in that start is asserted at the argv herdr is given. |
| C3 → C5/C6/C8 | The plan is produced **once**, printed in the brief, recorded on the node, and written as the trace's first line. C5 runs the `entry:` sections, C6 renders the `work:` ones, C8 runs the `exit:` ones — each takes the plan as input; none re-derives it. |
| C4 ↔ C5/C6/C8 | `Append(line)` on the way in or out of every step; `Refuse` is called by the gate, never by C4. C4 never gates; the gates read C4's file. |
| C8 ↔ C4 | The exit gate reads the trace and the node's `plan-recorded` payload and refuses per AC6. |
| C9 ↔ C4 | `fs trace <node> [--json]` reads only; text render ends with `deviation: <…>` or `deviation: none`. The file is located from the node alone — `--project` no longer selects it and survives, if at all, only as an assertion that the trace is the one the caller meant. |
| C9 ↔ C3/C8 | `fs batch <node>` reads only: exit 0 iff every member of the fan-out has a done integration naming it, and on success its payload carries the members — `node`, `worktree`, `worktree_path`, `branch`, `pane`, `project` — which is what `batch`'s `exit:` steps iterate to remove each member's resources, and what its branch postcondition reads per member: an empty `branch` is a member whose delivery did not create its worktree, which is the member that postcondition skips rather than refuses over. There is no separate enumeration command, and a batch with no members is refused rather than read as complete. `fs reviews <cap node>` is the same shape of read for the other cross-dispatch link: exit 0 iff a **done** dispatch carries `reviews: <cap node>` on its task-created payload **and names the revision it read** — `trace.Plan.Reads`, stamped by `Prepare` from the reviewed dispatch's own tree — and that tree stands at the same revision now, 1 otherwise, and the refusal says which of six facts it found. Four are facts about the link, and each is refused as itself rather than as the same absence: a node that does not exist is a typo, a node that is not a dispatch is not the thing a review reads, "nothing names this change" is a review not dispatched, and "something does and has not finished" is a review to go and finish — "nothing names it" is a claim about other dispatches, and it is not true of a name that resolved to nothing. The other two are facts about the revision, and a done review is necessary here and no longer sufficient: a review that names **no** revision — every review closed before `Reads` existed — is refused as **nameless**, because accepting it would reinterpret it as a review of the current revision, the claim it never made; and one whose revision the tree has moved past is refused as **stale**, naming both the revision it read and the one the tree stands at. `--without-review "<why>"` is the one way past either, and it is the sanctioned one for a close whose change was already reviewed under the older regime. `code`'s exit gate runs it before the teardown, and `--without-review "<why>"` is the recorded skip — exported to the exit steps as `$FS_WITHOUT_REVIEW`, so the playbook's guard is one visible line rather than a name fs matches on in Go. |
| C9 ↔ C2 | `fs kb list` prints each playbook's **scope** (`shipped`/`global`/`<project>`) beside its state, so a shipped playbook that has no file anywhere is listed rather than absent, and an override is marked as one. `fs kb add|edit --project P` writes to `~/.fs/projects/<P>/kb/`. |
| C10 ↔ files | Reads `src/flagship/defaults/kb/*.yaml` + `src/flagship/defaults/scripts/` + `skills/` + the `fs` usage text; asserts no playbook names an absent skill, an absent subcommand, a repo-relative path, or a bare `fs`, that every script a step runs through `"$FS_BIN" script <name>` is one the binary ships, and that no step names `$FS_SCRIPTS` at all. The subcommand check reads both spellings — bare and `"$FS_BIN"` — because `"$FS_BIN"` is a path expression, not a name, and the subcommand after it is the same question; it joins two words into one subcommand only where the specs have a two-word subcommand (`task get`, `kb prompt`), so the word after `script` is read as a script name and not as half of a subcommand that does not exist. It deliberately does **not** put `fs` on PATH to make the other tests pass: the exit gate's test env is the one place that would have hidden this, so the CLI tests leave the binary off PATH and a gate has to reach it the way a playbook does. |
| C11 ↔ C5/C8/C9 | The scripts are read out of the binary and nothing is written to disk: `Script(name)` returns the embedded body or an error naming every script the binary does ship, and C9's `fs script <name> [args…]` hands that body to `bash -c` with the process's own stdin/stdout/stderr and exits with the script's status. That last part is the contract, not an implementation detail: the script's exit status is fs's, so a gate run this way can fail — a wrapper that swallowed a non-zero status would leave every locked doc unchecked while every dispatch reported green. The body is passed as `bash -c <body> <name> <args…>`: bash reads the word after the command string as the script's `$0`, so without that placeholder the first argument becomes the script's name and `$1` is empty — the script receives **no arguments** and still does something plausible. Both env builders export `FS_BIN` from `os.Executable()` resolved to an absolute path; unreadable means exported **empty**, which a step must treat as missing rather than as a path. **A status is a value as well as a verdict.** `branch-decision.sh` uses it to answer *what to do* rather than *whether something went wrong*: 0 nothing to do, 1 delete the branch it prints on stdout, 2 usage, 3 refuse. fs neither parses nor knows that encoding — the pass-through is what makes it expressible at all — and the caller's obligation is one line: read the status, and treat the branch name on stdout as an authorisation rather than as a match. |

**The playbook set to author** (global; `~/.fs/kb/`)

| name | moments | applies_when | order | job |
|---|---|---|---|---|
| `cap` | cap | — | 10 | the cap's standing rules. The closed skill list is **deleted** — replaced by what the cap does, with `use:` hints for the skills that fit, stated as hints. Carries the missing-protocol rule: when `fs dispatch` refuses for want of a playbook, file a gap, never improvise. Carries the **order** rule as a step rather than a reminder: after a worker reports and before closing, dispatch the review with `--reviews <the work's cap node>`, read it when it closes, disposition what it found — because the gate that enforces the order fires too late to be the reminder, and a review dispatched after the close reviews a change nobody can act on. |
| `herdr` | cap | `engine=herdr` | 20 | herdr-operative rules, **rewritten to stop contradicting `cap`**: no waiting, no polling; `fs pending` is the read |
| `worker` | work | — | 10 | every worker's standing obligations, **moved out of `renderBrief`**: note your node, never invent one, **report a finding rather than filing it** — a gap node names the scope it belongs to, choosing that scope is a coordinating act, and a write into the cap's own scope is refused from a pane that holds a delivery record, so the obligation is the report and the cap files the node — put the exact commands and the commit in the node. **Declares `engine: herdr` and `agent: pi`** — the standing realization, being the one playbook with no `applies_when`, so a project shadowing it changes the harness for that project. A shadow names **only the fields it changes**: the one on this machine declares `agent:` and `agent_args:` and inherits `engine:` (AC4), so the engine it runs under is still declared in exactly one file |
| `code` | entry, exit | `code` | 10 | the code participant, one file. Its `entry`: `test -f AGENTS.md`, the locked-doc grep, `"$FS_BIN" script check-specs.sh` (a locked doc is a claim about the code at the commit it names, and this is the step that asks whether that claim has been overtaken — no commit has landed on the covered paths since the sha the marker names. It is not the step that asks whether the doc is still true; that takes a reader, and the `spec` participant is the one that reads), ask: a locked PRD names this one deliverable, ask: is the acceptance check stated. Its `exit`: ask: is the worker's node complete enough that nothing important died with its transcript, then the **deliverable check** — `"$FS_BIN" script check-deliverable.sh "$FS_BASE" "$FS_CARDS"`: HEAD has moved past the revision the project stood at when this dispatch was prepared, and the paths this dispatch's cards declare are committed rather than left in the tree. It is deliberately not a repo-wide clean-tree check, because this repo's tree is routinely dirty with another agent's work, and whether the code **works** is not checkable here and is not claimed — then the **review gate** — `[ -n "$FS_WITHOUT_REVIEW" ] || "$FS_BIN" reviews "$FS_NODE"`, a `check:` and not an `ask:` because it has a record behind it and `--confirm` must not wave it through, standing before the teardown because the teardown removes the tree a review reads, and standing **after** the deliverable check because committing after a review moves HEAD past the revision that review read, so a close that reviewed first would need a second review to satisfy a gate it met by doing what the check told it to do — then the **declared teardown** (branch, worktree, herdr workspace — the fix for a `dev-task --worktree` leaking), then the postconditions: one per resource the teardown claims to have removed — the checkout path, git's registration of it, the herdr workspace, and **the branch the delivery created**, which is the one resource the teardown destroys and nothing can re-make. Declares `engine: herdr` because those `do` steps call it |

**A shipped playbook may only name what the binary ships** — an `fs` subcommand *through `"$FS_BIN"`*, a generic POSIX tool, or a script the binary carries, run as `"$FS_BIN" script <name> [args…]`. `FS_BIN` is the running binary's own path, exported by the two env builders because a step cannot work it out for itself, and it is now the answer to both halves of the rule: the subcommand a step runs and the script it runs are addressed through the same path. C11 is the scripts: they are embedded in the same `defaults/` tree as the playbooks, read back out of the binary and written nowhere — so the rule's third clause is no longer a *path* at all, and the directory that made it one is gone. Before C11 `check-parallel.sh` lived in the repo's `bin/`, and a shipped gate could name a repo-local path that resolved in exactly one project: `batch`'s entry gate ran `bin/check-parallel.sh`, `integration`'s exit gate ran `tests/run.sh`, and each would have exited 127 anywhere else. C10 enforces the rule mechanically, because the failure is invisible in the repo that happens to have the file.

**The bare `fs` was the same defect wearing the other hat, and it shipped.** fs is installed into `~/.fs` and is not on PATH, so every step that ran a bare `fs` exited 127 — and a gate that cannot run does not refuse, it *fails*, which is indistinguishable from the work being wrong. Ten sites across four playbooks carried it — seven `check:` steps and three `do:` steps: one in `member`'s `exit`, one in `integration`'s `entry`, `batch`'s `exit` gate plus its three teardown actions and its three postconditions, and `code`'s review gate — and all ten now address the binary as `"$FS_BIN"`. The review gate is the one that had fired: its single live run died on `sh: line 1: fs: command not found` while every test around it passed, because the tests put `fs` on PATH and the playbook never does. That is why C10's rule is a *syntax* rule — no executed step may name a bare `fs` — and not a runtime one: a gate that only ever passed in the one environment that had `fs` on PATH was not checked by anything. C10 reads the subcommand out of `"$FS_BIN" <sub>` as well as out of a bare `fs`, so moving a step onto the exported path does not quietly stop checking the subcommand it names.

**The acceptance criterion this moves is upstream AC7**, whose sentence stays true but is now narrower than the test: it fails a shipped playbook naming "an `fs` subcommand `fs` does not implement", and the detector now *also* fails one that names that subcommand through a bare `fs`. The upstream line is left as it stands rather than restated — the card for this round named this document, AC7 is a partial description rather than a false one, and widening a locked acceptance criterion is the cap's call. What moves here is the third clause of this doc's own portability rule, above: the set of things a shipped playbook may name is now "an `fs` subcommand through `$FS_BIN`, a generic POSIX tool, or a script the binary carries through that same path", and the `code` participant's entry gate is the measure of it — a rule the binary ships and no step runs is the same failure as a step that names what the binary does not ship.

**Materialisation is gone, and C11 is what moved.** The scripts were the last artifact fs wrote to disk before running it, and the reason was one sentence: a playbook is *parsed by fs* but a script is *executed by the shell*, so `bash "$FS_SCRIPTS/<name>"` needed a real path. Reading the body out of the binary and handing it to `bash -c` removes the need rather than the requirement — there is no copy, so there is nothing to go stale, nothing to unlink when a script is dropped, and no write racing a concurrent `exec` of the same file. `MaterializeScripts` is deleted, not fixed: gaps `t-b3e6fe34`'s two defects (a dropped script never unlinked, `os.WriteFile` rather than temp-plus-rename) were defects *of the copy*, and the function they belonged to no longer exists. **C11 moves** — its job is "embed the scripts a playbook runs and run them out of the binary" — and **C9 moves** with it, gaining `fs script` on the enumerated surface. The playbook set is unchanged. No criterion in `playbook-system.md` moves: its AC7 names the *detector*, not the clause, and the sentence it carries stays true. What does change upstream is that doc's Scope bullet, whose third clause reads `"$FS_SCRIPTS/<name>"`, and it is revised in place with this one for the same reason the shipped playbooks are: a locked doc that states a rule the code no longer follows is the failure the whole corpus exists to catch.

**`engine: herdr` is declared by three playbooks**, for two different reasons. `worker` declares it as the **standing realization** — one of the two fields that decide how work is dispatched at all. `batch` and `code` declare it as a **constraint**, because their `do` steps call `herdr workspace close`; a plan resolving to a different engine refuses rather than running a herdr command into the void. `integration` no longer declares it: it lost the steps that needed herdr, and declarations are not kept out of habit.

**The shipped default became a scope, and two of this doc's criteria moved.** `~/.fs/kb/` used to hold a *copy* of every shipped default, and the copy won: a change to `defaults/kb/*.yaml` landed in the binary, passed its tests, and was **inert** on the install, because resolution read the file seeded from the previous default and nothing compared the two. The fix is not to seed harder — it is that the embedded tree is the **last candidate** of the same walk, so a file on disk is a candidate only when it is an **override** (`edited()`: a body that differs from the stamp it carries, or an unstamped body that differs from the shipped default), and a copy that restates the default is transparent whatever its age. **C2 moved**, and this is the criterion that carries the change: its contract is a three-scope walk whose last scope has no path, so the include stack holds a synthetic id (`"<shipped>/<name>.yaml"`) and the chain a playbook inherits down is the chain it resolves through — a project playbook with no user-scope copy below it inherits from the shipped default, which the old two-scope rule could not express because it assumed the copy existed. **C9 moved**: `fs kb list` scope values are now `shipped`/`global`/`<project>`, and `shipped` is a row for a playbook with no file anywhere — which is what makes "is my edit live" and "is my copy stale" answerable from one command instead of inferred from a directory listing.

**Two commands claimed to seed, and now one does.** `fs bootstrap` is **removed**, not deprecated: with the default resolving out of the binary there is nothing to install, and leaving a second command that writes playbooks to `~/.fs/kb/` would keep the copy-versus-scope question open in the one place it has to be closed. The honest replacement for "give me a copy I can edit" is `fs kb reset <name> --yes` — it writes the default to disk on request and is the only command that does. `fs kb diff` reads the copy rather than what resolves, so a copy that has fallen behind shows its drift; a diff taken through resolution would come out empty for exactly the file a reader runs the command to look at.

**No other criterion moved.** Not one shipped default's content changed, so C1's set is the set it was, and AC7, AC8 and AC9 upstream measure what they measured. The copies already on an install are left transparent rather than deleted: the moment this lands they stop shadowing, with no operator step and nothing to remove.

**The worker's gap obligation was the wrong half, and the guard was the right one.** `worker.yaml` told a worker to file a `kind: gap` node *naming the scope it belongs to*. From a pane that holds a delivery record that write is refused — correctly, by the guard `cap-role.md` owns — whenever the scope it belongs to is the cap's own, which is where the findings of a dispatched investigation land: the obligation asked for an act the mechanism forbids, and the worker that got around it by unsetting `HERDR_PANE_ID` was doing exactly the coordination the guard exists to prevent. So the obligation moved, not the guard. The replacement is the route the cap used by hand twice today: the worker **reports** the finding (`fs report <its node> --question --line …`) and the **cap** files the node — which `cap.yaml` already tells it to do when a dispatch refuses for want of a playbook. The `worker` row above is the statement that moved, and the two files are the shipped `worker.yaml` and `dispatch.Guard`'s refusal text, which now names that route instead of leaving a worker holding a finding with nowhere to put it. **No acceptance criterion moved.** The obligations are described in that row, not measured by a criterion; the honesty test over the changed default is C1's set unchanged, and the step is a `say:` whose prose no rule scans.

**The teardown asserted three resources and the branch was not one of them, and C9 is what moved.** The fixes to the branch step — `43ba143f`, `18be0780`, `3188ce67`, `98f9c376` — all worked on naming the branch to *delete*, and every one of the defects they closed has the same end state: `code`'s `exit` reached its last step with the delivery's branch still in git and the close reporting success. A branch step that matched nothing skipped in silence; one told a wrong path deleted a branch that was not the delivery's; the destructive form detached the project's own checkout and deleted the project's own branch. None of them could be seen from the close, because the close asserted the checkout path, git's registration of it and the herdr workspace — three things, and the branch, the one the teardown destroys with no copy anywhere else, was asserted by nothing. The postcondition is one `check:` in `code`'s `exit`, and the same assertion held over the fan-out in `batch`'s, where it names the member whose branch survived: a refusal over a loop that could only say "a branch was not deleted" names nothing a reader can act on, and the member is the address of the failure. Both read the branch from the **record** — the delivery writes it from what `herdr worktree create` reported, and an empty one stands the step down — and ask git only whether that name still resolves, which is `rev-parse --verify --quiet`'s three answers: 0 present and refused, 1 absent and passed, anything else a git that could not be asked and refused rather than passed, the same fail-closed shape the workspace postcondition passes only `workspace_not_found` to keep. **C9 moved**: the surface it enumerates gained a field, `fs batch`'s per-member `branch`, read by `dispatch.Batch` out of each member's own delivery record. **C8 does not move** — its job is to run the `exit` steps and refuse on any plan/trace gap, and a postcondition is a step like any other; nothing in the gate changed to make the branch checkable. **No criterion in `playbook-system.md` moved:** its AC6 governs whether a declared step ran *and was followed*, and the postcondition is declared, runs, and is asserted by the same trace rule as the steps beside it. What that change did not do is fix the branch step's logic: the sed-and-grep chain that names the branch to delete was left untouched, and the postcondition exists precisely because that step has been wrong repeatedly, and not in the same way each time. **One class is outside what it can see, and it is stated rather than left to be found:** a branch step that deletes the record's own branch *through* a guard that should have refused it — the default-branch guard stands down when the repository records no `refs/remotes/origin/HEAD` — passes this postcondition, because the name it asks git about really is gone. What that state needs is a **wrong record**, not a wrong tree: the assertion is over `$FS_BRANCH` itself, so it passes only when the name it asks git about *is* the branch that was wrongly deleted, and the delivery path cannot produce that state — the name arrives from `herdr worktree create`'s response, which fs passes no `--branch` to, so a delivery's record names the branch herdr generated and never the trunk's. The assertion is over the name the delivery created, not over the rules that govern deleting it; the second is the branch decision's own coverage, and it is where that hole belongs.

**The branch decision left the step, and C11 is what moved.** The defects those fixes closed — `43ba143f`, `18be0780`, `3188ce67`, `98f9c376` — were not one mistake per shell idiom, and they were not one defect either. Two are how the recorded path is spelled: `18be0780` left a symlinked final component unfolded, and `98f9c376` left `/x/.`, `/x/y/..` and a doubled leading slash unfolded, so the match against git's listing found nothing. Two are how the branch is named: `43ba143f`'s teardown part asked the checkout and skipped a worktree whose directory was gone, and `3188ce67` replaced the asking with git's own registration, because `git -C "$p" rev-parse` answers for whatever repository encloses `$p`. What the four share is a failure direction rather than a root cause — each ends with the step reporting success while the branch it was written to free is still in git. The defect the decision exists for was never the language; it was where the answer was assembled: inside the step, out of shell test results and a text match against git's listing followed by `[ -n "$b" ] || exit 0`, so "the match found nothing" and "there is correctly nothing to do" were the same value — empty stdout, exit 0 — and a branch that matched the wrong worktree was deleted. The decision is now `defaults/scripts/branch-decision.sh`, and it answers in its exit status, one state per status, never in the text it prints: **0** nothing to do, with nothing on stdout and nothing the script itself writes to stderr; **1** delete the branch named on stdout and nothing else; **2** the command line was wrong; **3** refuse, one line of reason on stderr. The safety is arithmetic rather than attention — **the status that authorises destruction is not the status of finding nothing** — so a caller that ignores the status has no name to delete unless the deletion was authorised, and a caller under `set -e` aborts on the assignment and deletes nothing at all. Both careless callers are tested against real repositories, because a seam that is safe in the tests and a foot-gun in the shell is the regression this shape invites; the third case in that test is the same careless caller on a state the decision *authorises*, so "nothing was deleted" is a statement about the contract rather than about a caller that never deletes anything.

Those findings are rows now rather than shell guards: the project's own checkout spelled any way (`//x`, `x/.`, `x/sub/..`, a symlink, `/private/tmp` for `/tmp`), a project root that is itself a linked worktree — where the repository's main checkout is a different directory — the trunk's own branch where no remote records a default, a branch another worktree holds, an unmerged branch, and a worktree standing on `HEAD` — a name git's listing prints in the branch slot that is not a branch name: `git check-ref-format --branch HEAD`, `git branch HEAD` and `git worktree add -b HEAD` all refuse it, so no delivery holds a branch by it, and while a ref of that name exists the repository cannot answer the name with one value — `git rev-parse HEAD` warns that the refname is ambiguous. That last state is in the set because the guard that used to answer for it, `[ "$b" = HEAD ]` in the step, was read as unreachable while this decision was written, on the argument that no branch is called HEAD; the state is buildable in one command, and what the decision answers for it is the rule rather than the incident — **a name that is not a branch can arrive in the branch slot, and the answer for it is nothing-to-do**. Each row asserts the status, stdout exactly, and what stderr had to say, and each row carries what its answer needs: the ones decided before git is asked anything run in a plain directory, and the rest are built on real scratch repositories, because a fact about which branch a worktree stands on cannot be stated to the decision without a repository holding it. They live in `cmd/kb_branch_decision_test.go` rather than under `tests/`, because the script is reached as `"$FS_BIN" script branch-decision.sh` and only the Go suite holds the binary and the scratch repositories these states need. Rules changed shape with them: a branch another worktree holds is found by counting git's registration lines for that branch — which is what `--ignore-other-worktrees` makes reachable, and what git would refuse to delete after the delivery's worktree had already been detached for it; the positional guard on the first stanza's *branch* is gone, because the fact about the main checkout is where it is — the guard asks whether the recorded path is that path, which is the same question as the project's own checkout, and refuses with the truth rather than naming the wrong one; and the checkout refusals now stand **above** the branch questions, decided from the listing before a branch is read, because which checkout a recorded path names does not depend on what that checkout stands on — with them below, a record naming the repository's main checkout answered nothing-to-do whenever that checkout stood on no branch or on `HEAD`, and the refusal was never reached at all.

The steps keep their lines: what moved is the decision, not the step. Both still declare it, both still run it, and both still *act* — the `resolve-path.sh` shape, where the script answers and the step does what the answer implies. Each step resolves the recorded path itself, because the act needs a path it can test for existence and hand to git, and the spelling a record carries is not one: a path spelled `$p/sub/..` is on disk while `[ -e ]` says it is not, which turns a live worktree into a pruned one. `batch`'s step passes the member as the script's label, so a refusal reads `member w1: branch … is not merged into HEAD` — the address of the failure, which the loop already knows and a reader should not have to reconstruct. **The postcondition from the first half stays where it is**, for the reason it was written for: the decision must not become the only place a rule lives, and a check that asks git whether the name still resolves is the one that catches the decision being wrong.

**C11 moves**: its contract carried the status pass-through as a mechanism — the script's status is fs's own — and it is now load-bearing as a *value*, because a non-zero status can be an instruction to destroy rather than a verdict on something that went wrong. `branch-decision.sh` exits 1 to say *delete*, and that is the only status on which it prints a branch name. **No criterion in `playbook-system.md` moves**: AC7's detector is over the *names* a playbook uses and covers this script like the others, and AC6 governs whether a declared step ran and was followed — the step is still declared, still runs, and its outcome is still appended. **One class stays outside the decision, and it is stated rather than left to be found:** the default-branch guard reads `refs/remotes/origin/HEAD`, and a repository with no remote records its default branch nowhere, so a branch that is the default only by convention — checked out nowhere else, recorded nowhere — is still deleted. "Nowhere else" is asked rather than assumed — the decision reads the branch out of git's registration of the path the **record** names, counts over git's whole worktree listing how many worktrees carry that branch, and refuses when more than one does. What no listing can answer is the other half. No arrangement of the repository's own facts closes the hole: deciding the default would mean knowing a convention this repo does not write down. The guard stands down **silently** — its stand-down arm short-circuits before anything is printed — and says so only in the comment where it stands down, and the postcondition cannot see it either, because the name it asks git about really is gone.

- `internal/knowledge/defaults.go` — `usedByFor` names the tags that load it **and the moments it serves** (derived from its sections + `applies_when`), not a name-suffix guess.
- `internal/knowledge/prompt.go` — selects the `cap:` sections of playbooks matching the session's tags; the header names the moments and the provenance.
- `internal/dispatch/dispatch.go` — tags, plan, `resolveRealization` (engine, agent and args, with the disagreement refusal naming both playbooks and both lists), entry steps, `plan-recorded` (now carrying the resolved engine, agent and args), `nextCommand` (the instruction that stands in place of a command: re-run with `--deliver`), `renderBrief` (work steps only). `--reviews` is validated by `reviewedDispatch` — the same `bareNodeID` + cap-scope + kind check `integrateMember` performs for `--integrates`, refusing a node that is not there and one that is not a dispatch with a distinct message each — and recorded as `reviews` on the dispatch's own task-created payload, so `Reviews` can answer from the record rather than from a goal string. `--fixes` is validated by `fixedDispatches` the same way and refused the same two ways, repeatable because a fix round answers more than one open dispatch in the ordinary case — the dispatch under review and the review whose finding it fixes are both open while the fix is made — and recorded as a decision on the fix round's own node. Those dispatches are open by construction, so naming them is the declaration that keeps the unresolved-dispatch gate from reading them as open work piled on top of the fix; without the flag they are, and the round needs `--allow-unresolved`.
- `internal/dispatch/deliver.go`, `close.go` — `loaded` lines; exit gate + trace gate. **`const agentKind = "pi"` and `const herdrEngine = "herdr"` are deleted**: the first becomes the resolved `agent:`, the second the resolved `engine:`. `agentStartArgs` builds the argv `Deliver` runs, and is the start command's only emitter: the printed line `nextCommand` used to carry named an agent no delivery record could reach, and is retired. The delivery record's `engine` field carries the resolved value rather than a constant, and its `branch` field carries the branch `herdr worktree create` reported for a worktree the delivery made itself — reported in the same response as the workspace id and the checkout path, so it is data the delivery already had — and is **empty** for a worktree named with `--worktree`, which came from elsewhere: that is how an exit step tells a branch that was never this delivery's to remove from one it failed to remove, without asking a question the tree is gone for. `exitEnv` exports `FS_WITHOUT_REVIEW`, the `--without-review` reason, empty when the flag was not given — the `FS_BATCH` precedent, where a step defers on a marker the close exports rather than on a convention — and `FS_BRANCH`, the delivery record's branch. **The reason may only claim a skip that happened, and recording it late is not enough to make that true.** Writing the decision after the exit phase succeeds rules out a waiver on a close that *failed*, but not one on a close that faced **no gate at all**: an abandoned close runs no exit check, and a plan without a review gate in it has none to stand down. Both refused the flag from the moment it existed (`close.go` asks the plan, not the flag) — `reviewGate(steps)` is true when some `check:` step in the exit phase defers on `$FS_WITHOUT_REVIEW`, which is fs's own exported marker rather than a playbook name, so the guard stays in the playbook where the gate is declared and fs matches on the variable it exports rather than on `code`. A close that faced no gate refuses rather than recording "waived the review gate" on a node whose close never met one. The reason is also **trimmed before it is tested**, so three spaces is refused with the empty case: a whitespace reason is the unrecorded skip the flag exists to prevent, wearing a disguise.
- `internal/trace/trace.go` (new) — append, read, render. The plan line carries `engine`, `agent` and `agent_args`, so `fs trace` shows the harness a dispatch ran under.
- `cmd/main.go`, `cmd/args.go` — `--tag`, `--also`, `--without`, `fs trace`, `fs script`, `kb` scope + `--project`, `--reviews` / `fs reviews`, and `--without-review` — which refuses a reason that is empty *after trimming* rather than reading it as a waiver, because an unrecorded skip is the one thing the flag exists to prevent, and refuses the flag outright on a close that faced no gate (abandoned, or a plan with no review gate in it). `dispatch`'s synopsis carries `--batch`, which it had omitted since `--batch` was added. Both env contracts name `FS_BIN` and no longer name `FS_SCRIPTS`: the entry gate's and the close's, each saying what a step does instead — `"$FS_BIN" script <name>`. A reader who finds `FS_SCRIPTS` in an older card learns there where it went.
- `defaults/kb/*.yaml` — the set above, embedded and resolved as the last scope, never written to disk by anything but `fs kb reset`. `cmd/kb_test.go` and `cmd/main_test.go` encode today's structure and must be updated to the new one — their *intent* (a gate is scoped to its own dispatch; the exit gate verifies what it removed) is preserved, not deleted. One assertion has since moved for exactly that reason: `code`'s exit used to be asserted to hold **no** pre-teardown check, on the grounds that neither a clean tree nor a merged branch can be made true here. The review gate is a check of that shape that *can* be answered — the cap dispatches a review — so the assertion now names the one check it admits and keeps the old rule by forbidding the repo-state kind (`git status`, `merge-base`) inside it, rather than by counting to zero.
- `defaults.go`, `scripts.go` (new), `cmd/script.go` (new), `defaults/scripts/*.sh` — C11. `//go:embed defaults` reaches the subdirectory; `Script(name)` returns a body out of the binary or refuses naming the scripts it does ship, and `fs script` runs it through `bash -c` with the name as `$0`. `checkEnv`/`exitEnv` export `FS_BIN` and nothing else about scripts — the `FS_SCRIPTS` entry is gone from both. Tests live beside the question the script asks — `tests/check-parallel/`, `tests/check-specs/` and `tests/resolve-path/`, each reading the script it exercises — except `branch-decision.sh`, whose answers are facts about git repositories and whose tests are therefore `cmd/kb_branch_decision_test.go`, beside the binary that ships it and the scratch repositories its states need. Neither of the two project-facing tests knows a project's layout — `check-specs.sh` measures against the whole project unless its caller narrows it with `--covered`.

## Failure modes

| Component | Dependency fails | Behavior |
|---|---|---|
| C1 | a step reads its input through a pipeline whose reader is missing | refuse, naming what could not be read. A pipeline's status is its **last** command's, so `"$FS_BIN" batch … \| jq -r … \| while` with no `jq` on PATH writes no rows, exits 0, and the step passes over every member — and the postcondition under it certifies, because a check whose body never ran reports success. The rule this states for step bodies: **the status that authorises a pass must not be reachable by a failure to look**. Both teardowns read in two assignments and refuse on either — `fs batch` into a variable (`fs`'s log line goes to stderr and is never folded into the data, which would hand `jq` a line that is not JSON), then that through `jq` into the rows, `jq`'s stderr captured so the refusal can quote it. `set -o pipefail` is not the fix: a step runs under whatever `sh` the host provides, and `pipefail` is a bash extension — a guard that is itself a portability gamble is the same defect one layer down. Its destructive twin is the rule `branch-decision.sh` is built on: **the status that authorises destruction must not be the status of finding nothing.** A decision that answers `0` both for "nothing to do" and for "delete this" cannot be read by a caller that only looks at whether it succeeded, and the fix is not a stricter caller — it is a status the deletion owns, and a branch name on stdout that reaches a caller on that status and no other |
| C2 | a project KB file is unreadable | refuse naming the path; never fall back to the global file silently (a silent fallback hides a broken project playbook) |
| C2 | `include` cycle / depth > 8 | refuse naming the chain; never hang |
| C3 | no playbook matches the tags | refuse per AC9 — an empty plan declares no engine and no agent, so the refusal names `worker.yaml`. The check is **per value**: a plan in which `code` declares the engine but nothing declares the agent refuses naming the *agent* alone, and says exactly that. The standing `worker` playbook carries no `applies_when` and matches every dispatch, so an empty plan means it was edited to stop matching |
| C3 | a matched playbook fails per-phase kind validation | refuse at dispatch, naming the playbook, the step and the allowed kinds — a broken playbook must not run half its steps |
| C3 | no playbook in the plan declares `engine:` or `agent:` | refuse naming `worker.yaml` as where to declare them. No fallback: a default in Go is the policy these fields remove. `agent_args:` is **not** part of this check — it is optional, and a plan declaring neither carries none |
| C3 | two situation-specific declarations disagree | refuse, naming both playbooks and both values. Neither the engine, the agent, nor the arguments are averaged. For `agent_args:` the refusal names both lists, because **concatenating them would be arbitration the user never sees** — the two playbooks' intent would be silently merged in an order nothing states |
| C3 | an `agent_args:` is present but names no term | refuse at parse, naming the playbook. An empty declaration claims arguments it does not name, and is also what a block list silently becomes |
| C3 | a top-level key is not in the schema | refuse at parse, naming the field and enumerating the schema. A dropped unknown line is a declaration fs never sees |
| C7 | the resolved `agent:` is one herdr does not know | herdr refuses the start; the existing rollback marks the worker node done with the reason and abandons the pane. fs holds no kind list to check it against |
| C7 | an `agent_args:` term is one herdr will not accept | herdr refuses the start; the same rollback handles it. fs validates no token — no flag grammar, no quoting, no shell — because the flag set is the agent's own |
| C4 | the log directory is unwritable | the step is a refusal: an outcome that cannot be recorded cannot be gated |
| C4 | a line is lost / the file is truncated | close refuses on the missing step (AC6). A truncated trace can only make close *stricter*, never looser — the failure direction is safe by construction |
| C5 | an entry `check` fails | refuse, trace line `fail` written first; `--confirm` records a decision naming the check and its output, as today |
| C6 | a `use:` names a skill the worker cannot load | the brief already says hints are not required; the worker proceeds. Not a gate |
| C7 | the brief cannot be sent | roll the worker node back as today; no `loaded` lines are written, so close refuses — a delivery that did not happen leaves a dispatch that cannot be closed as if it had |
| C8 | the change has no done review of it | refuse, naming the playbook, the step, and the `fs dispatch --type review-task --reviews <node>` that would answer it. `--without-review "<why>"` proceeds and records the reason as a decision on the node. A review dispatch is not caught by this: `code` is selected by the declared `code` tag, which it does not carry |
| C8 | `--without-review` on a close that faced no review gate | refuse, naming which of the two shapes it found — an abandoned close, which runs no exit check at all, or an exit phase with no gate in it (naming the playbooks it does carry). Recording a waiver there asserts a skip that never happened, which is the failure the flag exists to make visible. `--without-review` is the gate's own override and only means something where the gate stands |
| C8 | `--without-review` with a whitespace reason | refused as the empty case, because the value is trimmed before it is tested — `"   "` is not a reason, and recording it is the unrecorded skip this flag exists to prevent |
| C8 | herdr is unreachable at teardown | warning, not a refusal (unchanged); the trace records `skipped` with the reason |
| C9 | `fs trace` on a node with no trace | prints "no trace was written for `<node>`" and exits 1; never an empty timeline that reads as success |
| C11 | a playbook names a script the binary does not ship | `tests/playbooks` refuses the change (C10), and the runtime refuses too: `fs script <name>` exits 1 listing the scripts the binary does ship, so the step fails loudly instead of running nothing. A rename is a message rather than a silent no-op — this is the half `MaterializeScripts` got right by leaving the file absent, kept after the file went away |
| C11 | `fs script`'s own argument passing | the body runs as `bash -c <body> <name> <args…>`, the *name* occupying `$0`. Without it bash reads the first argument as the script's `$0` and `$1` is empty, so the script silently receives no arguments and often still does something plausible — `check-parallel.sh` exits 2 saying no cards were named. The failure is silent by construction, which is why the argument path is tested with a case whose answer depends on an argument |
| C11 | a step's script exits non-zero | that status is `fs script`'s own, and its output is streamed as it is written. Deliberately not an envelope: `check-specs.sh` exits 1 to say a locked doc is behind, and a wrapper that returned 0 would leave every locked doc unchecked while every dispatch reported green. A status may also be an **instruction** rather than a verdict — `branch-decision.sh` exits 1 to say *delete the branch on stdout* — which is why the status that authorises destruction is not 0 and why the name to delete is printed on that status alone: a caller that ignored the status would delete only what the script named, and one under `set -e` would delete nothing |
| C11 | `os.Executable()` cannot be resolved | `FS_BIN` is exported **empty**, and a step that runs `"$FS_BIN"` — a subcommand or a script — fails on the empty path rather than running some other `fs`. Deliberately not a fs-level refusal: a broken `~/.fs` must not block a dispatch whose playbooks need no binary of their own |

## Scale assumptions

- The shipped playbook set (`tests/playbooks/test_playbooks.py` measures it; the table above names each one), ≤ 30 total across both scopes; a plan of ≤ 12 steps; a trace of ≤ 200 lines per dispatch.
- **Dispatches are serialized per cap, and this is enforced rather than assumed.** The unresolved-dispatch gate counts unfinished cap-scope `kind: dispatch` nodes and refuses a new dispatch while any exists, subtracting the set of nodes the new dispatch declares a relation to — `--integrates`'s member, `--reviews`' node, `--fixes`' nodes, and the open children of `--batch`'s node, a review being by construction about a dispatch that has not closed, a fix round by construction repairing dispatches that are still open, and a batch's members by construction running alongside each other — and yielding to `--allow-unresolved`. The relation is the declaration and nothing else: a node id that merely appears in the dispatch's own text grants nothing, and every node these flags name was already resolved and refused-if-absent before the gate runs, so no dangling reference reaches it that way. The measure is the tests: `TestPrepareGatesOnOtherOpenDispatchesButNotOnTheMemberItIntegrates`, `TestCLIDispatchRecordsTheReviewsLink`, `TestPrepareGatesOnOtherOpenDispatchesButNotOnTheOnesItFixes`, and `TestPrepareGatesOnOtherOpenDispatchesButNotOnItsBatchSiblings`. This bullet used to claim "one dispatch in flight per cap", which was both too strong (a review runs alongside) and too weak (a fan-out is serialized too), and then stated the fan-out's cost as a consequence to pay. It is not one: **a member's siblings are the work it runs alongside, so a fan-out's members each dispatch with no `--allow-unresolved`** — gap `t-2f346ebd`, closed 2026-09-27.
- Steps are shell commands and file reads — p95 well under 100 ms each; the trace adds ≤ 2 ms per step.
- The trace is read by one process at a time (the cap); no locking beyond append-only writes. Concurrent readers are fine (whole-file read).
- Total trace storage is trivial (≤ 200 KiB per dispatch) and never garbage-collected by this change.
