# Spec — a playbook is a protocol for a kind of work, matched and ordered, and every step is on the record
Type: spec · Owner: cap · Lock state: the marker above, nowhere else

## Problem & who breaks

- **Who:** the user, as the cap's principal, on every dispatch; and the worker, who receives a brief.
- **Break 1 — the playbooks are wrong, not merely thin.** `cap.yaml` lists `nix-config` (no such skill) and tells the cap to dispatch `init-context`, `design-task`, `review-task` — dispatches `fs dispatch` **refuses** outright (no playbook selects them; verified against the built binary 2026-09-21). A contract that instructs the impossible is worse than none. *One third of this has since closed: `review-task` now has a protocol — see "Resolved since this doc was locked".*
- **Break 2 — one file cannot be both a gate and a brief.** `<type>-prerequisites` gates the cap *and* supplies the worker's context via its `say` steps. The name says gate, the payload says brief.
- **Break 3 — the worker role has no contract at all.** The gap-filing obligation and the "do not invent your own node" rule are **string literals in Go** (`renderBrief`, `internal/dispatch/dispatch.go`). Changing what every worker must do requires a rebuild.
- **Break 4 — selection is name equality, so it cannot express a situation.** `--type parallel` exists as a task type because "more than one task in worktrees" had nowhere else to go. `--type` is doing double duty as a type label and as a situation.
- **Break 5 — nothing records what ran.** The cleanup and integrate gates have never been exercised through a live close (gaps `t-8153023b`, `t-524b7dee`), and no dispatch leaves a trace, so adherence cannot be reconstructed after the fact or drawn.
- **Cost of doing nothing:** the cap keeps following a contract that is partly impossible; gaps filed against playbooks cannot be closed because there is no mechanism to close them into.

## Non-negotiable outcome

- A dispatch's **matched playbooks are all loaded, in order, and a gap between the plan and what ran fails the task** — proven by running a real `fs dispatch` → `fs close` cycle and reading its trace.
- Falsifiable: a dispatch whose plan has 5 steps and whose trace has 4 must be refused at close, naming the missing step. A tester passes or fails this without arguing.

## Scope in / out + primary flow

**In**

- Playbook schema: `name`, `applies_when`, `order`, the realization fields `engine`, `agent` and `agent_args`, `creates`, and **one section per moment the participant takes part in** — `cap:`, `entry:`, `work:`, `exit:`; step kinds `say`, `use`, `check`, `ask`, `do`, `include`. The key set is closed: a top-level key outside it is refused, not dropped.
- **How the work is realized is a playbook decision, not a Go constant.** `engine:` names the dispatcher a protocol's steps are written for; `agent:` names the kind of agent that runs the work; `agent_args:` names the arguments that agent is started with — comma-separated on one line, one argv element per term, so `--add-dir /tmp/x` is a single argument holding a space and not a shell string. All three resolve from the plan, so changing the harness — or what it is started with — is a file edit, never a flag or a rebuild; and a project-scope shadow that declares only the field it changes inherits the rest (AC4), so changing the harness for one project is one line in one file. fs validates none of the arguments' content: the flag set belongs to the agent, not to fs.
- Moments: `cap` (standing rules), `entry` (before the worker starts), `work` (the worker's brief), `exit` (at close). One file is one **participant** and may take part in several moments — a `member` is briefed at `work` and gated at `exit`, and both live in its one file.
- Plan resolution by tag matching + `order`, recorded on the dispatch node.
- Three scopes, resolved in this order: project `~/.fs/projects/<project>/kb/`, global `~/.fs/kb/`, and the defaults **embedded in the binary**. The last is a scope and not a copy of one: a file on disk participates only when it is an **override** of the shipped default — a body that differs from the stamp it carries, or an unstamped body that differs from the default — so a copy that restates the default, current or stale, is transparent and the default below it resolves. Nothing has to be written to `~/.fs/kb/` for the shipped set to run, and a change to a shipped default is live with no operator step. A name collision is an **override, not a replacement**: the higher playbook's declared fields and sections win, and every name it does not declare is inherited from the playbook below it — a project playbook with no user-scope copy under it inherits from the shipped default, because the chain is one chain. `include:` splices across the same scopes and is a separate mechanism from that inheritance.
- The trace: one JSONL file per dispatch with a trackable id and filterable properties; `fs trace <node>` renders it.
- The exit gate reads the trace: a missing line is a refusal.
- The shipped playbook set rewritten to protocol-per-situation, at the set `tests/playbooks/test_playbooks.py` measures; the mechanism doc's table names each one and says what it is for. The count is deliberately not restated here — a number in prose is a second place to update, and the measurer is the first.
- **A shipped playbook may only name what the binary ships** — through `"$FS_BIN"`, the running binary's own path: an `fs` subcommand, or a script the binary carries, run as `"$FS_BIN" script <name> [args…]`. A playbook in `defaults/kb/` runs in *every* project, so a path into one repo is a gate that passes there and exits 127 everywhere else — and a bare `fs` is the same failure with no path in it: the binary is installed into `~/.fs`, not into PATH.
- A test that fails when a shipped playbook names an absent skill, an absent `fs` subcommand, a repo-relative path, or a bare `fs`.
- **The refusal is the missing-protocol signal.** When `fs dispatch` refuses because no playbook selects the work, that is the mechanism correctly reporting that the protocol does not exist yet. `cap.yaml` stops claiming those dispatches are possible and instead says: file it as a gap, do not improvise.

**Out (non-goals)**

- **Not a redesign of the batch protocols.** The `parallel` and `integrate` gates are **re-filed unchanged** into the new schema — same steps, same order, only the header changes — so a batch dispatch behaves exactly as it does today. They are not rethought here because they were never clear and deserve a spec of their own; the one asset that must not wait is the declared worktree/branch/workspace teardown, which also **folds into `code`'s `exit:` section** so a `dev-task --worktree` stops leaking (gap `t-33799786`). `fs integrated` and the batch disjointness check stay as they are.
- **Not situations for `design-task` and `init-context`.** Deferred for the same reason: no protocol is written for them in this change, so dispatching those types still refuses — now visibly, as the missing-protocol signal above. (`review-task` stood in this non-goal too and has since been done, which is recorded below rather than dropped from here.)
- **Not a visual viewer.** Events and the text reader only; a canvas/HTML timeline is a later change.
- **Not per-project playbook *versioning*.** Project playbooks under `~/.fs/projects/<project>/kb/` are unversioned machine-local files. No shipped playbook needs one yet, so this is a latent property rather than an immediate cost — see assumption A4.
- **Not an obedience checker.** Nothing claims a `say`/`use` step was *followed*; see Non-functional requirements.
- **Not a change to the event store's task-state vocabulary**, beyond one additive `plan-recorded` event type.
- **Not a rewrite of `fs pending`/`fs sweep`/`fs integrated`.** `fs sweep` and `fs integrated` are untouched; `fs pending` has since gained the shared re-verification additively (`202ff717`) — the guard widened from *is it blocked* to *did it record a claim*, and the entries, states and counts it builds are unchanged — which is recorded here rather than left as a bare absolute. **No acceptance criterion moved.**
- **Not a general condition language.** `applies_when` matches presence and equality only — no ranges, no negation.
- **Not a second engine adapter.** `engine:` is a *constraint* today, not a choice: fs has a herdr adapter and nothing else, so a plan declaring another engine can only refuse. The field is what makes adding one a playbook-visible change rather than a code change — it does not itself add one.

**Primary flow (one path, step by step)**

1. Cap tags the work: `fs dispatch --project P --type dev-task --tag code --goal "…"`.
2. `fs dispatch` resolves the **realization** first — the AC9 refusals fire here, before anything is written or created — then builds the tag set (`type=dev-task`, derived, declared), selects every playbook whose `applies_when` is satisfied, sorts by `order`, and prints the plan.
3. **The cap node is created before the entry steps**, because the trace is named after it and an entry step's outcome has to have somewhere to land. Then the plan is recorded twice: as a `plan-recorded` event on the node (which the exit gate reads) and as the trace's **first line** (which `fs trace` prints before any step has an outcome). Either write failing refuses.
4. `entry` steps run fail-fast, one trace line each. A failing check **does not refuse "before a node is created"** — the node already exists, and it is marked `done` with the refusal as its decision, so the attempt stays legible and no open dispatch is invented. This ordering is forced by the naming in step 3, not chosen for convenience.
5. `--deliver` hands the brief over. The brief carries: goal, the `work`-phase playbooks' `say`/`use` steps **in plan order**, the `cap`-phase obligations, the checklist, the locked docs, and the worker's node. The handoff appends a `loaded` line per `work` playbook.
6. Worker works; the cap closes with `fs close --node … --decision "…"`.
7. `fs close` re-reads the plan and the trace; a required step with no outcome, or a matched `work` playbook never handed over, refuses. Then `exit` steps run, then the pane and declared teardown.
8. `fs trace <node>` renders the whole thing — plan, steps, statuses, deviation.

## Acceptance criteria

- **AC1 — selection.** `fs dispatch --project P --type T --tag k=v` selects exactly the playbooks whose `applies_when` is satisfied by the dispatch's tags (`type=T` plus derived plus declared), sorted by `order` ascending, ties broken by name. The brief prints the plan with each playbook's phase and order.
- **AC2 — the plan is durable.** The plan is recorded on the dispatch node as a `plan-recorded` event carrying the ordered list and the tag set. `fs trace <node>` prints the plan before any step has an outcome.
- **AC3 — every step is on the record.** Each entry and exit step appends exactly one line to `~/.fs/traces/<project>.<node>.jsonl` carrying `ts`, `id` (`<node>/<playbook>/<step>`), `dispatch`, `project`, `playbook`, `moment`, `step`, `kind`, `status`, `duration_ms`. The path is **flat**: the file records a *dispatch*, whose identity is the cap node, so it is filed where the dispatches are rather than under the project it acted on. The project **leads the name** so a person browsing the directory recognises the file — one file is one project — and `project` is a field on every line as well, for the program. The `worker` field is present on every line written once a worker node exists — the `loaded` lines and the exit lines. An entry line cannot carry it: the worker's node is created at delivery, so at entry there is nothing to name, and a placeholder would be a fabricated field. A failing step appends `status=fail` **before** the command refuses.
- **AC4 — scopes merge.** A project-scope playbook with the same `name` as a global one **overrides the fields and sections it declares and inherits every name it does not**, uniformly: `applies_when`, `order`, `engine`, `agent`, `agent_args`, `creates`, and each moment section. A file declaring no `work:` runs the global `work:`; a file declaring `work:` keeps its own. **Declared and absent are different, and the difference is presence, not value:** a declared field wins even when its value is empty, so `applies_when:` with no terms is a deliberate standing declaration and does not inherit the terms below, while an absent `applies_when` takes them. A shadow that declares nothing but its name would inherit everything and so **changes nothing** — it is refused, naming that, because a no-op that reads as a deliberate override is worse than no file. `include: <name>` splices that playbook's steps at that position, resolved in the same scope order. Inheritance and `include:` are **distinct and ordered** — inheritance decides which fields and sections the playbook has, then the splice fills them — so a shadow whose file says `work: - include: <its own name>` ends with the global steps exactly **once**, never twice; that shape is what every shadow on this machine has, and a duplicate would silently double every worker's standing obligations. An include cycle is refused with a message naming the cycle, not a hang or a stack overflow. `fs kb get` **marks the inherited names**, because the cost of inheritance is that a shadow stops being self-describing. This is proven by test, and now also live: `integration`'s suite check reaches a plan from a project playbook (`~/.fs/projects/skills/kb/verify.yaml`, a *different* name joining the same plan by tag rather than a shadow), so a shipped gate and a project's own check land in one plan.
- **AC5 — the brief is the `work` phase.** The brief carries the `work`-phase playbooks' `say` and `use` steps in plan order, each `use` as `<skill> — <when>`, under a heading stating the skills are hints and that no skill is required. No worker obligation remains a Go string literal.
- **AC6 — loaded and followed, or it failed.** `fs close` refuses when, for the recorded plan: an `entry`/`exit` step has no trace line; any step's last line is `status=fail`; an `ask` was not confirmed; or a matched `work` playbook has no `loaded` line at delivery. The refusal names the playbook, the step index, and the kind. A missing trace file is a refusal, never a pass.
- **AC7 — the set cannot rot.** A test under `tests/` fails when a shipped playbook names a skill with no `skills/<name>/SKILL.md`, or an `fs` subcommand `fs` does not implement, **or a bare `fs` at all** — the binary is installed into `~/.fs` and not into PATH, so `fs reviews "$FS_NODE"` is a step that exits 127 wherever it runs. The subcommand check reads the name out of `"$FS_BIN" <sub>` as well as out of a bare `fs`, so a step that addresses the binary correctly is still checked for what it asks it to do. `bash tests/run.sh` runs it.
- **AC8 — it builds and it passes.** `nix build` for the flagship package, `go test ./...` under `src/flagship`, and `bash tests/run.sh` are all green.
- **AC9 — the harness is declared, not coded.** `engine:`, `agent:` and `agent_args:` are playbook fields, and a dispatch resolves all three from its plan: no Go constant or literal **supplies** any of them. Literals that only check or report what the plan already decided do remain, and none of them is a source: the herdr adapter runs the `herdr` executable, and a plan whose *resolved* engine is not `herdr` is refused — the one-adapter constraint Non-goals states, which is why `engine:` is a declaration and not yet a choice. Which literals those are, and how many, is deliberately not written down here: the grep the verification plan names is their measurer, and the criterion is met when every hit of it has been read and accounted for. A literal that decides what a dispatch runs, rather than checking or reporting what the plan already decided, is the thing this criterion forbids. The standing declaration — a playbook whose `applies_when` is empty — is the default; a situation-specific declaration overrides it; two situation-specific declarations that disagree **refuse, naming both playbooks and both values**. A plan that declares neither `engine:` nor `agent:` refuses, naming `worker.yaml` as where to declare them — `agent_args:` is optional and is never the reason for that refusal. The arguments inherit independently of the kind: a playbook that overrides `agent:` and declares no `agent_args:` keeps the standing ones, and there is no way to declare "no arguments" — an `agent_args:` present but empty is refused. The resolved engine is the `engine=` tag, and all three values are recorded on the dispatch and in its trace, so which harness ran, and with what, is reconstructible from the record alone.

## KPIs & failure signal

- **Good:** every closed dispatch has a trace that accounts for every planned step — ratio 1.0, read from `~/.fs/traces/`.
- **Off-switch:** a dispatch closes with **no trace at all**, or its plan holds **nothing but the standing `worker` playbook while its tags should have matched more**. The second is what broken selection looks like now that an undeclared plan refuses (AC9) instead of arriving empty: the tags matched something, but not what they named. Either signal means selection or recording is broken and the playbook layer is inert — the exact state this change replaces. On that signal, stop and fix selection before dispatching anything else.

## Non-functional requirements

- **Honesty of the claim — the one that cannot be waived.** The trace records `loaded` for `say`/`use` steps, never `followed`. There is no mechanism, and none is to be added, that claims a worker obeyed guidance. Whether guidance was obeyed is the review dispatch's judgement, and the refusal text must say so where it could be mistaken for obedience.
- **A condition that cannot be checked ships as an `ask:`, and says which it is.** `independent-review`'s exit closes the loop only when every finding is dispositioned — `fixed` and verified, `filed` as a named `kind: gap` node, or `accepted` with its reason on the node. No `check:` can decide that from the store, and none was written: a fixed finding leaves no record of itself, an accepted one is a sentence, and a review that found nothing is indistinguishable from a review that never ran. A check that could not fail would be worse than the ask, being a gate that reports compliance it never tested (the `t-49bcbdb2` shape, where a verify printed a tick over a blank page). So the step is an ask, its refusal is real — `fs close` will not close a dispatch whose ask is unanswered — and the playbook's own comment says plainly that the cap's answer is a judgement this mechanism cannot audit. **The deeper reason was sequencing, and it is now closed — by making a skipped review visible, not by producing one.** The review *follows* the close it reviews (the review that found the defect this protocol was written for was dispatched at 13:26Z, after both closes it read, at 09:19Z and 12:50Z), so at close time it has not happened and no close-time check can see its findings. What can be asked at close time is the other question: *did a review of this change finish at all*. That question has a record behind it, and the record is a link. `--reviews` is the link: `fs dispatch --type review-task --reviews <cap node>` validates the named node exactly as `--integrates` validates a member and records it on the review's own task-created payload. `fs reviews <cap node>` reads it the other way round — exit 0 iff a **done** dispatch carries that link **and names the revision it read while the reviewed tree still stands at it**, 1 otherwise, and it says which of the six facts it found, because they send the cap to different places: an id that resolves to nothing is a typo, a node that is not a dispatch is not the thing a review reads, "nothing names this change" is a review not dispatched, "something does and has not finished" is a review to go and finish, a done review that names **no** revision is refused as nameless because fs will not read it as a review of this change — every review closed before the field existed stands there, and the way past is either review the change again or close with `--without-review "<why>"` — and a done review whose revision the tree has moved past is a review of an earlier state of the change, to be run again. `code`'s exit gate runs it as `"$FS_BIN" reviews "$FS_NODE"` — the binary by its own path, because `fs` is not on PATH and a bare `fs` there exits 127, which is what the gate did on its one live firing while every test around it passed. `code`'s exit gate runs it before the teardown, so a close whose change has no done review of it **refuses, naming the command that fixes it** — and the one way past is `--without-review "<why>"`, which proceeds, exports `FS_WITHOUT_REVIEW` to the exit steps, and records the reason as a decision on the node. A skip is therefore visible rather than impossible, and *visible* is the whole claim: this does **not** dispatch the review. A cap that passes `--without-review` on every close is back where it started, with the one difference that matters — the skip is on the node, in the cap's own words, where a reader finds it. `skills:t-8aed1d4d`, filed for this exact sequencing defect, is what `--reviews` and `fs reviews` are; direction (c) of `cap:t-b20e5812` is what the gate closes. Direction (a) of that gap — a mechanism that *produces* the review — is not built and is not claimed here.
- **Cost:** the log adds ≤ 2 ms per step, ≤ 1 KiB per line. A step's **command output is never logged** — status and duration only, so a check that prints a secret cannot write it into the trace.
- **Reliability:** a trace write failure is a refusal, not a warning — the gate cannot prove what it cannot record. The trace is local disk under `~/.fs`; no network, no egress, no new dependency.
- **Compatibility:** existing on-disk playbooks that still carry `type:`/`trigger:`/`engine_scope:` are **refused** with a message naming the replacement field; they never half-work. `fs kb reset` restores every shipped default.
- **Observability:** `fs trace <node>` renders one dispatch; the JSONL is `jq`-filterable on every field. Both, not either.
- **Operations:** a project with no `~/.fs/projects/<project>/kb/` behaves exactly as global-only. Absence of a project KB is never an error.

## Data requirements

- **Inputs required:** the playbooks the binary embeds, plus `~/.fs/kb/*.yaml` (global playbooks) and `~/.fs/projects/<project>/kb/*.yaml` (project playbooks) where they exist — each parseable under the mechanism doc's schema; dispatch flags `--type`, `--goal`, `--tag`, `--worktree`. Both on-disk scopes may be absent: a fresh home with no KB at all resolves the shipped set, and an absent directory is never an error.
- **Outputs produced:** the plan (on the node, as `plan-recorded`), the brief (handed to the worker), the trace (JSONL, one line per step outcome).
- **Must survive:** the trace must outlive the worker's transcript and the pane — that is its entire purpose. It is **not** deleted at close; `fs trace` reads a closed dispatch's trace afterwards.
- **Empty record:** no log file → AC6 refusal, and `fs trace` says *"no trace was written for `<node>`"* rather than printing an empty timeline. An empty `applies_when` matches every dispatch (a playbook that is always loaded); a dispatch whose tags match no playbook yields an empty plan, which **refuses** per AC9, since an empty plan declares no engine and no agent. The standing `worker` playbook has no `applies_when` and therefore matches every dispatch — so an empty plan arises only when it has been edited to stop matching, and that is the thing to fix.

## Rollback & recovery

- **Playbooks:** files. A scope is an override or it is not there; there is nothing to re-seed. `fs kb reset <name> --yes` writes the shipped default to disk, `fs kb diff <name>` shows what a copy has drifted from, and a copy is removed by hand (`fs kb remove`, or deleting the file). Reverting the playbook layer alone is a file operation with no build.
- **Go:** reverts by commit. The store is untouched apart from additive `plan-recorded` events, which derived state ignores — so a revert leaves no state to clean up.
- **"Reverted" means:** `fs kb list` reports `shipped` for every playbook the binary carries — no copy participates anywhere — `fs kb diff` is empty for every copy that remains, the trace files stay on disk as evidence, and no dispatch in flight is left open.
- **The one failure that would wreck it:** a trace that passes the gate while disagreeing with what ran — i.e. a fabricated or silently truncated log. Mitigation is structural, not procedural: the same process that runs a step writes its line, close refuses on a **missing** line, and a write failure is a refusal — so passing AC6 requires having run the steps.

## Security & compliance

- **Secrets:** the trace records step bodies, status and duration — never command output (see NFR). Step bodies are already on disk in the playbook file, so the trace adds no new exposure.
- **Destructive actions:** `do` steps run only in an `exit:` section, appear in the recorded plan before they run, refuse on failure, and never run before the gate's checks and asks. `--abandoned --reason` remains the explicit, recorded escape.
- **Provenance:** every line carries the dispatch node, the playbook, the step and the timestamp; the trace is append-only and local to `~/.fs`, never transmitted.
- **N/A:** no regulatory obligation applies, no personal data is processed, no new network egress, no credential is read or stored by this change.
